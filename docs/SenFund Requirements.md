# SenFund Software Requirements

6 November 2026 · Implementation and release criteria for the USD invoice → USDT settlement → INR payout flow

**Product goal.** An Indian freelancer issues a USD invoice to an overseas business. The client pays USDT from a wallet. Both parties can verify settlement, and the freelancer can trace an eligible INR payout back to the original invoice. Keep the two milestones separate. The hackathon demonstrates public testnet settlement and simulated payouts. The production pilot requires an approved funds flow and real bank credit evidence.

**Routing decision.** For this build, fallback is allowed only when Mudrex is unavailable before any payout request or deposit. After any dispatch or transfer with an uncertain outcome, freeze routing and reconcile the original attempt. A later switch requires an explicitly approved policy and auditable operator action.

## Integrated sponsor architecture

**End-to-end sequence.** The freelancer configures an ENSv2 subname and its Whitechain payment address. SenFund resolves it at invoice creation and signs the recipient into the invoice. Checkout independently resolves the same name and validates the signed request and its trusted settlement configuration before asking for wallet approval. Whitechain settles the test USDT. After the verifier confirms the transaction, Chainlink CRE combines onchain identity and offchain evidence to decide whether the simulated payout can proceed. The receipt shows the confirmed settlement and the separate payout decision and result.

**Boundaries.** Ethereum Sepolia hosts ENSv2 records. Whitechain Sepolia holds and transfers the official test USDT. CRE reads ENSv2 on Ethereum Sepolia and uses HTTP to consume SenFund's Whitechain verification output and a fixture provider's status. The demo uses separate chain configurations. CRE gates payout after settlement, so the independently hosted checkout can still settle while the SenFund backend or CRE runner is offline. No test token leaves Whitechain for an exchange or bank.

### 2 Chainlink

**Target prize.** Best workflow with CRE, the $1,500 track. It accepts a successful CRE CLI simulation or a live CRE deployment. The workflow must connect a blockchain to an external system and be used meaningfully. The separate $3,500 CCIP prize requires contract-level CCIP use that changes onchain state. The CRE workflow below is scoped to the CRE prize. [Official Mumbai prize terms](https://ethglobal.com/events/mumbai/prizes) · [CRE EVM capabilities](https://docs.chain.link/cre/capabilities/evm-read-write)

![Chainlink architecture](SenFund%20Architecture/SenFund%20Chainlink%20Architecture.png)

- **CL-01 · Implement the gate.** Run a CRE HTTP-trigger workflow through the CLI for a confirmed invoice. Use an EVM read against the ENSv2 Universal Resolver on Ethereum Sepolia to re-check the chain-specific recipient. Use CRE HTTP calls to read canonical Whitechain receipt evidence from SenFund and availability or prior-order status from a separate demo provider endpoint. Verify the exact invoice digest, receipt identity, recipient and environment. Use configured endpoints and pass only opaque references and public chain fields.
- **CL-02 · Apply the workflow result.** Return `USE_MUDREX`, `USE_P2P`, or `HOLD` with the reason, receipt reference, environment and payout attempt key. A trusted demo runner binds the result to the current receipt and consumes it once. Reject stale or replayed decisions. Re-check that the payment is still confirmed immediately before dispatch. Missing or conflicting evidence, an ENS recipient change or an uncertain prior attempt yields `HOLD`. Only confirmed pre-dispatch unavailability permits P2P.
- **CL-03 · Capture sponsor proof.** Commit the workflow, configuration template, redacted trigger input and reproducible CLI command. Save a successful run that performs the chain read and HTTP calls, and show the resulting state change on the SenFund dashboard. Demonstrate the hold and safe fallback cases. Label the CRE run as a CLI simulation and the provider API as a fixture.

### 3 ENS

**Target prize.** Best Use of ENSv2, the $7,000 track. It accepts Ethereum mainnet or Sepolia and requires a functional live demo and public code. Use the official ENSv2 deployment on Ethereum Sepolia for the new-build target. Confirm the team's event lane. The separate $3,000 existing-project Continuity prize specifies Ethereum mainnet, so a Sepolia submission does not cover that track. [Official Mumbai prize terms](https://ethglobal.com/events/mumbai/prizes) · [ENSv2 deployments](https://docs.ens.domains/learn/deployments/)

![ENS architecture](SenFund%20Architecture/SenFund%20ENS%20Architecture.png)

- **ENS-01 · Issue and control a real merchant subname.** Under a parent controlled by the team, use an ENSv2 Permissioned Registry and a dedicated Permissioned Resolver. Set the explicit Whitechain Sepolia address record using ENSIP-11 coin type `0x80000752`. Use Enhanced Access Control to grant a dedicated operator rights only over that coin-type field on the dedicated resolver. Keep registry ownership and resolver upgrade rights with the owner. The delegate must be unable to edit other fields or upgrade the resolver. [ENSv2 registry](https://docs.ens.domains/ensv2/permissioned-registry/) · [ENSv2 resolver](https://docs.ens.domains/ensv2/permissioned-resolver/) · [ENSIP-11](https://docs.ens.domains/ensip/11/)
- **ENS-02 · Use live resolution to authorize checkout.** Pin the enrolled merchant's signing address and normalized ENS name outside the URL. Resolve the name via the official ENSv2 Universal Resolver on Ethereum Sepolia. Require the explicit chain-specific record and reject a missing record or default-address fallback. Put the resolved address in the signed invoice. Checkout re-resolves and compares before wallet approval. Never replace a signed destination using a later record. A changed or unavailable record stops checkout until the issue is resolved or a new invoice is signed.
- **ENS-03 · Capture sponsor proof.** Provide a reachable live demo and public source. Show the configured name and resolver, an onchain record change, a stale invoice blocked before approval and a replacement invoice that resolves correctly. Demonstrate that the delegated updater cannot modify an unauthorized record. Keep names and records free of client, invoice and bank data. ENS record control is separate from beneficiary verification and KYC.
